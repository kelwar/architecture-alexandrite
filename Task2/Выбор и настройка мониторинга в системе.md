### Мотивация

На данный момент система имеет две основные проблемы: жалобы пользователей на затерянные во времени заказы с последующей потерей контрактов, а также, долгое открытие страницы оператора в MES.

Мониторинг позволит с помощью различных измерений понять поведение сервисов, выявить и устранить задержку в открытии страницы оператора, что должно существенно увеличить скорость обработки заказов.

### Выбор подхода к мониторингу

Для выявления причин потери заказов, в части продуцирования сообщений системой CRM-API в очередь RabbitMQ, а также считывания сообщений из очереди в MES-API, будем использовать метод RED. 
Важно использовать информацию о пропускной способности RabbitMQ и MES-API, о количестве неудачных запросов в секунду и времени, которое требуется на их обработку.

Для выявления причин задержки при загрузке страницы актуальных заказов также будем использовать подход RED.
Здесь важен показатель длительности (Duration) - собранный с помощью распределенной трассировки, этот показатель поможет отследить запрос на загрузку главной страницы оператора, отследить его прохождение в MES-API, и далее время считывания сообщений из RabbitMQ.
В совокупности эти 2 подхода должны помочь ответить на вопросы: как долго считывались новые сообщения из очереди, сколько непрочитанных сообщений было в этот момент в очереди, возникали ли при этом ошибки, как долго запрос из АПИ шёл в приложение MES.
В качестве инструмента будем использовать Prometheus и Grafana для визуализации.

Метрики:
1. Number of dead-letter-exchange letters in RabbitMQ - позволит определить количество необработанных сообщений (помеченных как dead-lettered). Необходимы метки с причиной (cause): названия меток "ttl_expired", "query_length_limit_exceeded", "negative_acknowledgement_by_consumer", "delivery_limit_reached_for_quorum_queries". 
Эти метки помогут более детально изучить причины потери сообщений, если таковые случаи имеются.
2. Number of message in flight in RabbitMQ - слишком большое количество сообщений "in flight" может указывать на риски по утере сообщений. Метки не требуются.
3. Number of requests (RPS) for CRM API - с меткой method_name="set_status". Интересует только момент установки статусов заказам.
4. Number of requests (RPS) for MES API - общее количество запросов для выявления пиковой нагрузки на АПИ.
5. Memory Utilisation for MES API - без меток. Проверим, справляется ли память с пиковой нагрузкой.
6. Memory Utilisation for MES db instance - успевает ли БД MES сохранять полученную информацию во время пиковой нагрузки.
7. Number of connections for MES db instance - метки operation="read" и operation="write" для определения пиковой нагрузки на чтение и запись раздельно.
8. Response time (latency) for MES API - с меткой method_name="get_orders". Интересует прохождение запроса на получение заказа, с учётом предыдущих метрик по кол-ву соединений к MES db и утилизации памяти.
9. Number of simultanious sessions for MES API - если в пиковые момент значение близко к максимальному, это может быть одной из причин некорректной работы страницы оператора.
11. Kb provided (sent) for CRM API - с меткой method_name="set_status". Позволит обнаружить разницу между подготовленными запросами на установку статуса заказа и реально отправленными (т.е. обнаружить наличие потерь на стороне CRM API).
12. Kb tranferred (received) for MES API - данные, переданные в MES API. Например, при считывании из RabbitMQ. В случае расхождений передано/получено - это может сигнализировать о потере сообщений о заказах к обработке.

### План действий

1. Создать docker-compose для запуска Prometheus.
2. Настроить приложения-экспортеры для сбора метрик с CRM-API, RabbitMQ и MES-API.
3. Создать конфиг-файл prometheus для сбора данных из экспортеров.
4. Настроить Grafana для визуализации данных метрик.
5. Локализовать участки возникновения проблем на основе данных мониторинга.
