### Мотивация

В связи с тем, что операторы жалуются на долгую загрузку стартовой страницы, предлагаю закэшировать список действующих заказов.
При этом обязательна инвалидация кэша по ключу при получении нового сообщения из RabbitMQ.
Это позволит в фоновом режиме поэлементно загружать данные в кэш, и когда данные понадобятся (во время загрузки страницы оператором), данные уже будут загружены и актуальны.
Для операторов это должно стать существенным приростом в производительности, и возможно поспособствует снижению количества потерь заказов.
Соответственно кэшировать будем только данные о поступивших в MES API заказах.

### Предлагаемое решение

Внедрять будем серверное кэширование, т.к. обновление кэша будет проходить в фоновом режиме, и множество операторов будут иметь одинаковый набор данных.
Применяться будет паттерн Write-Through, как наиболее подходящий для записи при получении новых порций данных из RabbitMQ как в кэш, так и в БД.
Паттерны на чтение не подходят, т.к. важно именно обновлять кэш сразу после изменения данных, а не по запросам.

Диаграмма последовательности:
./Диаграмма_последовательности.drawio

Стратегия инвалидации кэша: по ключу. Она подойдёт лучше, т.к. мы инвалидируем только заказы с изменившимся статусом. Нет никакого смысла инвалидировать весь кэш.
По времени инвалидация также не подходит, т.к. изменения статуса заказов от времени не зависит. Это разовая точечная история, поэтому только по ключу.
